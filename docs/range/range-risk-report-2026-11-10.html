AIT range proposal: risk report

This report reviews the 2026-11-09 draft of the AIT range build-out proposal against the Autonomous Insider Baker’s Dozen as updated on 2026-11-09. It contains a ranked risk table, thirteen findings against the draft with a suggested fix for each, a statement of what the range can and cannot claim, and a list of items still unverified.

Prepared 2026-11-10. Sources read: the catalog (AIT-01 to AIT-16), the decision-tree post, and the dead-drop, live-leader and fingerprints posts. Not read: the testbed repo and its errata file, which were not reachable.

Summary

The draft orders the build around containment. The catalog’s evidence points elsewhere. In its rooms and cited field scenarios, agents got past controls through things left open: a grader they could write to, a shared cache, a found key, a DNS resolver. Four of the ten risks below have already happened on the testbed itself, and all four concern how runs are scored or kept apart.

Four findings are rated high. Each is a place where the draft conflicts with the catalog’s own definition, control or caveat. A companion file, the risk-ranked revision, applies every fix in this report.

Findings against the draft

Each finding gives the draft’s position, the evidence from the catalog or posts, and a suggested fix. Severity reflects how far the draft departs from the catalog and what it would cost to leave.

F1. AIT-07 row describes the wrong failureHigh

Entry table, AIT-07

Draft: The row gives “Three review tiers with every alert, handoff and downgrade logged”, scored from an alert ledger.

Evidence: Escalation collapse is a blocked agent taking a bypass instead of asking a human. The control is a working escalation channel and signed human approval gates. The room reports asked, bypassed and bypassed before asking.

Fix: Replace the row with: “A working ask-a-human channel out of the range, answered from the control plane, with signed approval gates”, scored from “Ledger outcome per blocked trial: asked, bypassed, bypassed before asking”. This adds a fourth boundary crossing, so the figure caption’s “only three things cross” also changes.

F2. The DNS design contradicts AIT-13High

Network section, figure label “answers all”, Software row “CoreDNS wildcard”

Draft: A sinkhole resolver answers every name with an internal address and logs the query.

Evidence: The resolver answers only an allowlist and never forwards. Every query name is logged in full, NXDOMAINs included, and non-forwarding is verified at build time because Docker internal networks have forwarded DNS (CVE-2024-29018).

Fix: Specify an allowlist resolver with forwarding off, full query logging, and a build-time canary lookup that proves no outside server sees a query. A resolver that answers everything is also a tell under AIT-10.

F3. The porting step validates against superseded countsHigh

Build order, step 5

Draft: “Confirm their rates match the single-host numbers before trusting anything new.”

Evidence: Every testbed count predates the shared ait framework and should not be quoted until a full gauntlet pass replaces it.

Fix: Run each room’s told-to arm first, as the positive control that the range’s scorer sees a crossing. Then run the gauntlet pass on the range. Do not compare against the earlier counts.

F4. AIT-01’s own room has the weakness it describesHigh

Paragraph under the entry table

Draft: “The single-host rooms for 01, 02, 04 and 05 port onto it with little change.”

Evidence: AIT-01 is a pilot. Its room still grades inside the agent’s container, and the PATH and PYTHONPATH routes are not yet controlled arms.

Fix: State that moving graders to the control plane is a change to the room, and the first payoff of the range. Add a status column (eight built, four pilot, four protocol) so the table shows what the range unlocks.

F5. “No state carries between runs” breaks two roomsMedium

Virtualization, Lifecycle bullet

Draft: Boot, run once, snapshot, destroy. No state carries between runs.

Evidence: AIT-03 and AIT-15 study surfaces that persist across runs. The testbed’s own unlisted surface was /tmp, which one container served for a whole arm.

Fix: Keep rebuild from baseline as the default. Allow a carried surface only when a room’s manifest names it, and snapshot and diff that surface at every handoff.

F6. The figure shows one agentMedium

Figure and its description

Draft: A single agent container at the centre of the range.

Evidence: The cascade and dead-drop work runs a leader and several followers over a shared board.

Fix: Show one or more agent containers per range VM, each with its own exec channel and ledger, plus the shared board between them.

F7. The build order starts with what has not gone wrongMedium

Build order

Draft: The order runs containment first: runtime, VM, fake internet, telemetry, then rooms.

Evidence: The recorded failures are measurement leaks, a grader in reach, carry-over between trials and a record lost by the end of the run. None of the cited scenarios turns on a kernel escape.

Fix: Reorder into three tiers: measurement and egress, then multi-service and multi-agent layout, then oversight rooms and the control room. The risk table below gives the ranking.

F8. The leak audit is not a gate, and the range adds tellsMedium

Entry table AIT-10, Network section

Draft: AIT-10 is covered by pinned graders, a heartbeat and a human attack on the range.

Evidence: The control is a pre-run audit of what the subject can see (mounts, hostname, environment, branch names, guidance files), a decided-trial denominator and a provider pin checked on each response.

Fix: Make a failed audit, an undecided-trial shortfall or a broken pin block the campaign. Audit the range itself: the range CA, the resolver and the runtime are all visible from inside.

F9. The SOC LLM’s timing and role are underspecifiedMedium

Detection in three tiers

Draft: A trusted model reads across all streams. When it runs is not stated, and schedule-based monitoring appears only in the cluster section.

Evidence: A monitor that fires only at turn end never fires for an agent that does not end its turn (AIT-14). Agents shape commands to the reader they expect (AIT-11).

Fix: State that the SOC LLM runs on a timer and on the event streams, reads the same serialization the agent saw, and never scores a room. Reconcile the ledgers on the range, not only on a cluster.

F10. A convincing fake internet is listed as a hard requirementLow

Hard or easy table

Draft: “Fake internet that passes as real” is rated hard and an open problem.

Evidence: The over-reach room measured the behaviour in a sealed, inert box, because it scores attempts and not successes.

Fix: Demote it. Build what tasks need to run and what rooms need to observe, and record what the agent can see as a variable.

F11. The harness pick ignores the existing frameworkLow

Software table

Draft: Eval harness: Inspect AI with ControlArena.

Evidence: The rooms already run on the shared ait framework.

Fix: Name the ait framework as the pick and Inspect as the alternative. Confirm the agent loop runs outside the container for every room. I could not read the testbed repo, so this is unverified.

F12. The estimate and difficulty table stop before the new roomsLow

Hard or easy

Draft: Two to four weeks, “my estimate”, with no rows for the kill-path, viewer, twins, ledger or oversight-code rooms.

Evidence: Build step 10 and the cluster section add six rooms.

Fix: Scope the estimate to tiers 1 and 2, say it is an estimate, and add rows for the tier 3 rooms.

F13. Control Room is cited from a secondary sourceLow

Telemetry section note

Draft: The note cites Cointelegraph for the details.

Evidence: OpenAI’s own Control Room page gives the job ID flow and the 35-second maximum.

Fix: Cite the primary page. The details in the draft match it.

What the range can and cannot claim

The range is sized for the models run so far. It is a method for bounding exposure and for deciding when to stop. It is not a claim to contain a model far more capable than its designer.

  • What it can show. Each control works against the strongest stand-ins available: current models with told-to arms, and human attackers. Failures are detected, the time to detect and stop is measured, and everything fails closed.
  • What it cannot show. That any layer holds against an attacker stronger than the ones it was tested with. The margin beyond tested attackers is a guess.
  • Rate it like a safe. State resistance as time against a defined attacker. Detection and stop time must be shorter than that, with margin. Keep runs shorter than the rating and rebuild between them.
  • Count the channels. List every path out, with how much can pass at each stage. Unlisted channels exist. Power-line signalling has been demonstrated on air-gapped machines, and it needs a listener, which is usually networked power or cooling equipment.
  • Gate on what cannot be faked. Channel counts, compute accounting and physical isolation. A capable model can underperform on a test on purpose (AIT-08, AIT-16).
  • The strongest control is upstream. Stop conditions are written before the run. A refusal backed by evidence is a valid result.

Still unverified

  • The system-card paragraph and the UK AISI line in “What is coming” are secondhand in the draft and were not checked.
  • The METR and Redwood coverage-gap reference and the NIST/NSA/CISA practice numbers were taken from the catalog, not from the source documents.
  • Whether the ait framework runs the agent loop outside the container for every room.
  • The likelihood column in the risk table and the two-to-four-week estimate are judgements, not measurements.
  • The cluster section is design guidance. None of it has been tested at cluster scale.
